在方案评审和技术讨论中，兼容性与上下游常被混用。本文界定两者的定义与方向约定。

## 一、兼容性：向后 vs 向前

- **向后兼容（Backward Compatible）**：新版本继续支持旧版本产生的数据或旧客户端，即新系统能打开、处理旧版本的数据。
- **向前兼容（Forward Compatible）**：旧版本能处理新版本产生的数据或协议扩展，即旧系统能在一定范围内打开、处理未来版本的数据。

命名的主体是「版本的动作」：新版本向后回头兼容旧数据，因此称 Backward；旧版本面向未来兼容新数据，因此称 Forward。中文习惯按时间轴理解为「向后是过去、向前是未来」，角度不同，容易混淆。

也可用「上/下」表述层级关系：

- **向下兼容 = 向后兼容**：高版本兼容低版本（新系统兼容旧系统）。
- **向上兼容 = 向前兼容**：低版本兼容高版本。

### 示例：Word 文档版本

- Word 2024 打开 Word 2010 文档 → Word 2024 向后兼容（新支持旧）。
- 通过补丁使 Word 2010 能打开 Word 2024 的新格式文档 → Word 2010 具备向前兼容能力（旧支持新）。

### 向后兼容为何是常态

实际开发中，向后兼容通常是刚需，向前兼容是特例：

- 用户的存量数据多由旧版本产生，新版本若无法读取，用户就不会升级。
- 向前兼容要求预见未来格式并预留扩展接口，成本高、收益不确定。
- 厂商通常不会让旧版本免费获得新能力，以免削弱升级动力。

例外之一是 HTML 等标准：老浏览器能打开多数新网页，是因为其会忽略无法识别的标签和属性，跳过不支持的内容，这是向前兼容的容错设计。但这只适用于新增内容可被安全忽略的场景；若新版本改变了既有标签的语义，或依赖新的解析规则，老浏览器仍无法正确呈现。

## 二、上下游：方向的判定

「上下游」借用水流的比喻：水从上游流向下游。在软件中判定上下游，取决于所讨论的「流」的方向，需要区分两种流：

1. **数据流**：源 / 生产方（producer/source）是上游，消费方（consumer）是下游，数据从上游流向下游。
2. **请求流**：调用方（caller）是上游，被调用方（callee）是下游；响应沿相反方向回流，即由下游返回上游。

### 示例：电商系统

调用链：用户 App → 网关 → 订单服务 → 库存服务 → 数据库

以「订单服务 → 库存服务」为例：

- 订单服务发起调用，是上游；库存服务接收请求，是下游。请求方向为上游 → 下游。
- 库存服务处理完成后将响应返回订单服务，响应由下游 → 上游回流。

### Git 中的上游

Git 语境中，**上游（upstream）指主仓库或源分支**，fork 出的仓库是下游。需要定期从上游拉取更新，因为代码源头在上游。

### API 依赖与演进中的上游

在 API 依赖与演进的讨论中，一种常见约定是按依赖关系命名：**提供 API 的一方（provider）是上游，使用该 API 的客户端（client/consumer）是下游**，依赖方向为下游 → 上游。

这与请求流的标签相反：请求流中调用方是上游，而在 API 依赖命名中，被调用的 provider 反而是上游。两种约定都成立，但混用会导致方向判断矛盾，因此同一文档或讨论中应明确采用哪一种。

## 三、兼容性与上下游的关联

上下游与兼容性经常同时出现：

- 上游升级 API、修改字段结构，下游需要适配，此时上游的改动可能破坏向后兼容。
- 若下游客户端不升级，上游在协议更新时须保证向后兼容，使旧客户端继续可用。

## 四、总结

- **兼容性看时间版本**：向后兼容 = 新支持旧；向前兼容 = 旧支持新。
- **上下游看流向**：数据流中源（上游）生产、消费方（下游）消费；请求流中调用方是上游、被调用方是下游，响应反向回流。
- **API 依赖命名**：provider 为上游、client 为下游，与请求流中调用方为上游的约定相反，使用时需明确。
