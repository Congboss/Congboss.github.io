在方案评审和技术讨论中，兼容性与上下游常被混用。本文界定两者的定义与方向约定。

## 一、兼容性：向后 vs 向前

- **向后兼容（Backward Compatible）**：新版本继续支持旧版本产生的数据或旧客户端。
- **向前兼容（Forward Compatible）**：旧版本能处理新版本产生的数据或协议扩展。

命名主体是「版本的动作」：新版本向后兼容旧数据，故称 Backward；旧版本面向未来兼容新数据，故称 Forward。中文常按时间轴理解「向后是过去、向前是未来」，角度不同，容易混淆。

也可用「上/下」表述：

- **向下兼容 = 向后兼容**：高版本兼容低版本。
- **向上兼容 = 向前兼容**：低版本兼容高版本。

### 示例：Word 文档版本

- Word 2024 打开 Word 2010 文档 → Word 2024 向后兼容（新支持旧）。
- 使 Word 2010 能打开 Word 2024 的新格式文档 → Word 2010 具备向前兼容能力（旧支持新）。

### 向后兼容的取舍

向后兼容通过延续既有数据与客户端契约来降低迁移风险，通常是默认要求；向前兼容要求预见未来格式并预留扩展接口，成本与不确定性更高。

HTML 等标准是向前兼容的典型：老浏览器忽略无法识别的标签和属性，从而跳过不支持的内容。该机制仅适用于新增内容可被安全忽略的场景；若新版本改变既有标签语义或依赖新的解析规则，老浏览器仍无法正确呈现。

## 二、上下游：方向的判定

「上下游」借用水流的比喻。判定上下游取决于所讨论的「流」的方向，需区分两种流：

1. **数据流**：生产方（producer/source）是上游，消费方（consumer）是下游，方向为上游 → 下游。
2. **请求流**：调用方（caller）是上游，被调用方（callee）是下游；响应沿相反方向回流。

### 示例：电商系统

调用链：用户 App → 网关 → 订单服务 → 库存服务 → 数据库。以「订单服务 → 库存服务」为例：

- 订单服务发起调用，是上游；库存服务接收请求，是下游。
- 库存服务将响应返回订单服务，响应由下游 → 上游回流。

### Git 中的上游

Git 语境中，**上游（upstream）指主仓库或源分支**，fork 出的仓库是下游；需定期从上游拉取更新。

### API 依赖中的上下游

在 API 依赖与演进中，一种常见约定是按依赖关系命名：**提供 API 的一方（provider）是上游，使用该 API 的客户端（client/consumer）是下游**，依赖方向为下游 → 上游。

该命名与请求流的标签相反：请求流中调用方是上游，而此处被调用的 provider 是上游。两种约定都成立，混用会导致方向判断矛盾，同一文档或讨论中应明确采用哪一种。在该约定下，上游修改 API、字段结构或协议时，下游需适配，否则可能破坏向后兼容；因此上游通常须保证向后兼容，使旧客户端继续可用。

## 三、要点

- 兼容性看版本：向后兼容 = 新支持旧；向前兼容 = 旧支持新。
- 上下游看流向：数据流生产方 → 消费方；请求流调用方 → 被调用方，响应反向回流；API 依赖命名中 provider 为上游、client 为下游，与请求流相反。
